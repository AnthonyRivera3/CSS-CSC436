Review & Refactor

Same markup. Two stylesheets. Spot the difference.

Every case below renders live, twice — once with the CSS we typically write first, once with the CSS after review — plus a real line-by-line diff of the two stylesheets. Read the diff, then look back at the two frames and connect each change to what it did.

How to read this page

  • Diff shows both renders side by side and the changes between the stylesheets. + green lines were added, − red lines were removed, grey lines are unchanged context, and ⋯ marks a run of unchanged lines that has been folded away.
  • Before / After show one version on its own with its complete stylesheet, for when you want to read it top to bottom.
  • Every preview is a real sandboxed <iframe>. Right-click → Inspect works inside them. Do that.
How we run this in class: the frames go up first with the code hidden. You tell me what looks wrong and what you would change. Then we open the diff and see how close you got.
Case 01Layout

The card grid that only works at one window size

Floats and a fixed pixel width. It looks perfect on the machine it was written on, and falls apart everywhere else. Narrow both frames by shrinking your window and watch which one survives.

What changed, and why

  • Floats → grid. Floats were a hack for a problem grid solves directly. The overflow: hidden on the parent existed only to contain the floats; with grid it is not needed at all.
  • margin-right → gap. Margin puts a gutter after the last card too. gap only goes between items, and it never collapses.
  • width: 200px → minmax(min(200px, 100%), 1fr). Cards are now at least 200px and share the leftover space. The min(200px, 100%) is the part that stops overflow on a phone narrower than 200px.
  • Equal heights, free. Grid items stretch to their row by default. The floated version leaves ragged bottoms.
  • px → rem for font sizes. Now the component respects a reader who has set a larger default font size.
Case 02Components & a11y

The button that hates keyboards

It looks fine. It is unusable without a mouse, it ignores the page's font, and it has no disabled state. Press Tab inside each frame and watch where focus goes.

What changed, and why

  • outline: none is deleted. This is the single most damaging line in beginner CSS. It removes the only signal a keyboard user has about where they are. It is replaced by an explicit :focus-visible ring, which shows for keyboard focus and stays out of the way on mouse clicks.
  • font: inherit. Form controls do not inherit the page font. Without this line your button is rendered in the operating system's UI font while everything around it isn't.
  • cursor: pointer. Cheap, expected, missing.
  • A :disabled state. The markup already had a disabled button; only the "after" stylesheet acknowledges it.
  • Hardcoded hover colour → color-mix(). The hover shade is now derived from the base colour. Change --btn-bg once and every state follows.
  • px padding → em. Padding now scales with the button's own font size, so a large variant needs one declaration, not three.
Case 03Centering

Centering that breaks the moment the text gets longer

The absolute-position-and-translate trick works — until the content is taller than the box you guessed at. Both frames have identical text.

What changed, and why

  • height → min-height. This is the actual bug. A fixed height is a promise the content cannot keep. min-height says "at least this tall, and grow if you must".
  • Absolute positioning → place-items: center. Two words replace five declarations, and the element stays in normal flow — so it can push the parent taller instead of spilling out of it.
  • width: 320px → max-width: 42ch. A reading measure instead of an arbitrary number, and it shrinks on narrow screens instead of forcing a horizontal scrollbar.
  • padding added. Once the box can grow, padding guarantees the text never touches the edge.
Case 04Cascade

The !important war

The current page's link is supposed to be highlighted. In the "before" frame it simply isn't — and no amount of extra CSS on .is-current will fix it. This is a cascade problem, not a styling problem.

What changed, and why

  • The !important is gone. It was beating .is-current outright. Nothing you write in a normal declaration can win against it — you would have had to escalate with a second !important, and now you have a war.
  • Id selector → class. #nav a scores 1,0,1. That single id makes the rule harder to override than any reasonable class combination, which is exactly what tempted someone to add !important in the first place.
  • .is-current → [aria-current="page"]. The accessible attribute is already in the markup and already tells assistive technology which link is current. Styling from it removes a duplicate source of truth that can drift.
  • @layer declares intent. state comes after base, so state rules win — regardless of specificity, forever. New base rules can never accidentally out-specify a state.

The demo markup carries both the id and the class so the same HTML can be styled by either stylesheet. In real code you would drop the id and the is-current class along with the old CSS.

Case 05Motion

Animation that makes the browser do too much work

Both bars animate. Only one of them can be handed to the compositor — the other forces a full layout pass on every single frame. Hover the panels too.

What changed, and why

  • transition: all → a named list. all transitions properties you never intended, including ones added later by a different developer. It is also the reason for surprise animations on page load.
  • margin-left → translateX(). Animating a margin re-runs layout for the element and its siblings 60 times a second. A transform is composited: no layout, no paint.
  • Animating width → scaleX(). Same reason. Set the element to full width, then scale it — transform-origin: left makes it grow from the correct edge.
  • A prefers-reduced-motion block. The bar still communicates progress; it just stops moving for anyone who has asked their OS for less motion.

To see the cost yourself: DevTools → Performance → record a few seconds over each frame. The "before" timeline is full of purple Layout bars; the "after" one is nearly empty.
